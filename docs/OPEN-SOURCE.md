# 开源协作与维护方案

状态：开源准备方案，不代表远端仓库、许可证或发布流程已经生效。

## 1. 项目身份与授权

拟名：DSH Task Shelf／任务资料夹。仓库名 dsh-task-shelf，npm 推荐使用维护者命名空间，避免名称冲突。

对外说明：独立社区项目，面向 DeepSeek Harness，不使用暗示官方认证的命名或标识。

推荐 MIT，理由是便于个人使用、分发和社区贡献。发布前由项目所有者确认版权主体与许可证，加入完整 LICENSE；在此之前不把本方案写成“已采用 MIT”。

复制第三方代码前记录仓库、固定 commit、许可证、修改范围，并保留必要声明。官方接口文档的使用不等于可不加审查地复制实现。图标、字体、截图和测试素材也要核验来源。

## 3. README 的对外要求

首屏回答：
1. 解决什么问题，附合成数据截图。
2. 项目当前是 alpha、beta 还是可用发行版。
3. 精确支持哪些 DSH 版本、平台和界面。
4. 怎么安装、停用、卸载和恢复。
5. 读什么、写什么、是否联网、数据保存在哪里。
6. 已知限制与故障报告渠道。

安装命令必须指向已发布且验证过的具体版本。开发分支和未测发行版不能放在普通用户的默认安装路径。已有文档从“设计”改为“已实现”时必须附证据。

## 4. 贡献规则

- 主分支受保护，变更通过 PR；不得由文档测试通过推断代码可用。
- UI 修改附前后截图；使用合成内容，避免真实会话和路径。
- 数据格式、权限使用、网络、依赖或发布流程变更需要特别标记并审查。
- 新增依赖需说明用途、为何不能复用已有能力、体积／许可／维护状态。
- 每个 PR 写清行为变化、相关测试和回退影响。
- 破坏兼容性与迁移修改同步更新版本声明和升级文档。
- 不接受通过关闭安全检查、篡改宿主安装、默认强制版本豁免来“修复兼容”。

首版尽量由一个维护者负责合并与发布，避免未经必要审查的高权限协作。后续再按实际贡献增加角色。

## 5. Issue 与漏洞报告

普通 Bug 模板：插件版本、DSH 版本、操作系统、桌面／Web、复现步骤、预期与实际行为、脱敏日志。

功能请求模板：使用场景、现有做法、具体障碍、验收例子。避免只积累模糊愿望。

SECURITY.md 在公开前必须提供真实可用的私密报告渠道。优先在 GitHub 启用 Private Vulnerability Reporting 并实测入口；若不可用，提供维护者确认过的安全邮箱。渠道未确定时不能放占位邮箱冒充可用服务。

提醒报告者不要公开 API key、完整聊天、配置、导出文件或用户目录。漏洞修复过程给出受影响版本、修复版本、临时缓解和验证范围。回应时间由维护者确认，不虚构 24 小时支持承诺。

## 6. 后期维护机制

- 新 DSH 版本发布后，在隔离环境运行兼容探测；通过后才扩大 engines.dsh。
- 自动探测是未来 CI 设计，本轮未创建定时任务或自动化。
- 定期依赖更新由 PR 提出，不自动合并关键依赖升级。
- 每次发行维护 CHANGELOG、支持矩阵和恢复说明。
- 首版只认实际测试过的组合；用户自行尝试其他版本时明确标为实验性。
- 严重故障优先恢复用户数据与宿主可用性，再处理功能需求。
- 后续若无力适配新 DSH，标记最后支持版本，停止暗示持续维护；保留导出、历史安装包、迁移说明并允许接任维护者。

## 7. 里程碑与公开时机

可以先公开方案与技术验证仓库，但标为 design/experimental，README 不提供生产安装承诺。

建议首次面向普通用户推荐的条件：
- 完成一个明确宿主版本上的真实安装测试；
- 已验证重启、停用、卸载、数据恢复；
- Release 中有包校验、测试摘要及已知限制；
- 有可用漏洞报告渠道、许可与第三方声明；
- 有旧包和经过验证的回退说明。

## 8. 发布前仍需用户确定

以下不阻塞本轮方案：
- GitHub 个人账号或组织、最终仓库名；
- 版权署名与许可证选择（推荐 MIT）；
- 希望首发支持的实际 DSH 版本及桌面／Web；
- 可接受的维护范围和安全报告渠道。

公开发布时再针对具体仓库和候选包执行授权步骤；本方案不表示已经发布，也不承诺无限期维护。
